# 02. 깃허브(GitHub) 구조 분석 — "버전과 협업" 층

> 한 줄 요약: 깃허브는 **코드를 담는 상자(저장소)와, 그 상자를 여럿이 고쳐 나가는 절차**의 집합입니다.
> 우리에게서 깃허브가 맡을 자리는 "경험팩이 버전별로 좋아지고, 누가 고쳤는지 남고, 문제를 신고하는 구조"입니다.

※ 기능 설명은 2026년 기준 일반적으로 알려진 구조입니다. 세부 화면은 4단계에서 실제 사이트를 다시 확인합니다.

---

## 1. 깃허브는 어떻게 생겼나 — 3층 구조

```
사용자 / 조직 (개인 계정, 회사·학교 계정)
 └─ 저장소 (Repository)                       ← "프로젝트 상자" 하나. 파일 + 설명서(README) + 기록
     ├─ 코드 (파일들, 버전 기록)
     ├─ 이슈 (Issues)            ← "고장 신고·요청 게시판"
     ├─ 풀 리퀘스트 (PR)          ← "이렇게 고치면 어때요?" 제안서
     ├─ 토론 (Discussions)       ← 질문·아이디어 게시판
     ├─ 릴리스 (Releases)        ← "1.2 버전 나왔어요" 공식 배포본
     └─ 자동 작업 (Actions)       ← 올릴 때마다 자동 테스트
```

쉽게 말하면, **레딧은 "글"이 중심이고 깃허브는 "물건(프로젝트)"이 중심**입니다.
대화(이슈·토론)도 전부 어떤 물건에 딸려 있습니다.

## 2. 핵심 기능과 "왜 있는가"

| # | 기능 | 무엇인가 (쉬운 말) | 깃허브에 왜 필요한가 |
|---|---|---|---|
| G1 | 저장소 | 프로젝트 하나 = 상자 하나 | 파일과 기록과 대화를 한곳에 모으려고 |
| G2 | README (설명서) | 상자 첫 화면에 보이는 안내문 | 처음 온 사람이 "이게 뭐고 어떻게 쓰나"를 바로 알게 |
| G3 | 버전 기록 (커밋) | 언제 누가 무엇을 바꿨는지 전부 기록 | 잘못되면 예전으로 돌아가려고, 누가 고쳤는지 알려고 |
| G4 | 릴리스 + 변경 내역 | "1.2 버전: 넘어짐 줄였음" 같은 공식 배포본 | 쓰는 사람은 "안정된 버전"만 받고 싶어서 |
| G5 | 스타(★) | 마음에 드는 저장소에 별 | 북마크 겸 인기 지표 |
| G6 | 포크 (갈래 복사) | 남의 저장소를 통째로 복사해서 내 것으로 고치기 | 원작자 허락 없이도 내 방식으로 바꿔 보게 |
| G7 | 풀 리퀘스트 (고침 제안) | "이렇게 고쳤는데 원본에 합쳐 주세요" | 여럿이 하나를 같이 좋아지게 |
| G8 | 이슈 (고장 신고) | "이 버전에서 이런 문제가 나요" 신고, 열림/닫힘 상태 | 문제를 빠뜨리지 않고 끝까지 추적하려고 |
| G9 | 이슈 템플릿 | 신고 양식 ("로봇 기종, 버전, 증상, 영상") | 신고마다 필요한 정보가 빠지지 않게 |
| G10 | 라벨 | 이슈에 [버그] [요청] [도움 필요] 꼬리표 | 많은 신고를 분류하려고 |
| G11 | 토론 (Discussions) | 이슈와 별도인 Q&A 게시판, "답변으로 채택" 기능 | 고장 신고와 일반 질문을 섞지 않으려고 |
| G12 | 자동 작업 (Actions, CI) | 올릴 때마다 자동으로 테스트 돌리고 ✅/❌ 표시 | 사람이 매번 확인하지 않아도 "망가졌는지"를 알게 |
| G13 | 라이선스 표시 | "자유롭게 써도 됨(Apache-2.0)" 등 | 남의 것을 써도 되는지 분명하게 |
| G14 | 토픽(주제 태그) | 저장소에 #robotics #microduck 같은 태그 | 같은 주제 저장소를 모아 찾게 |
| G15 | 프로필 + 기여 그래프 | 사람 페이지, 1년 동안 매일 활동을 잔디처럼 표시 | 이 사람이 얼마나 꾸준히 기여했는지 보여 주려고 |
| G16 | 조직 계정 | 회사·학교 단위 계정, 멤버 권한 관리 | 단체가 함께 관리하려고 |
| G17 | 팔로우 / 지켜보기(Watch) | 사람·저장소의 새 소식 받기 | 관심 있는 것의 변화를 놓치지 않게 |
| G18 | 의존성 표시 | "이 프로젝트는 저것이 있어야 돌아감" | 설치 전에 필요한 것을 알게 |
| G19 | 후원 (Sponsors) | 제작자에게 매달 후원 | 오픈소스 제작자 보상 |
| G20 | 보안 경고 | "이 버전에 알려진 위험이 있어요" 자동 알림 | 위험한 버전을 쓰지 않게 |

## 3. 깃허브에서 배울 점과 조심할 점

**배울 점**
- **"물건에 대화가 딸린다"는 구조**가 우리에게 맞습니다. 경험팩 하나에 후기·질문·고장 신고가 딸려야 "이 팩 괜찮나?"를 한 페이지에서 판단할 수 있습니다.
- **버전과 되돌리기**는 사업계획서의 핵심 기능(되돌리기)과 정확히 같은 생각입니다. "1.2에서 넘어짐이 늘었다 → 1.1로 돌아가기"가 가능해야 합니다.
- **자동 테스트 ✅ 표시(Actions)** = 사업계획서의 **시뮬레이터 검증 배지**입니다. 깃허브가 이미 "자동 검사를 통과했다는 표시를 사람들이 믿는다"는 것을 증명했습니다.
- **포크(갈래 복사)** 는 "우리 집 마루에 맞게 속도만 낮춘 문워크" 같은 **변형 팩**을 만드는 데 그대로 쓸 수 있습니다. 원작이 누구인지도 자동으로 남습니다.
- **신고 양식(이슈 템플릿)** 은 초보자 질문의 질을 크게 올립니다. "로봇 기종·펌웨어·바닥 종류·영상"을 처음부터 받으면 답하기 쉬워집니다.

**조심할 점**
- **깃허브의 말(커밋, 풀 리퀘스트, 브랜치)은 일반인에게 외국어입니다.** 개념만 빌리고 말은 바꿔야 합니다 (예: 포크 → "내 버전 만들기", 이슈 → "문제 알리기").
- **풀 리퀘스트(고침 제안)는 우리 사용자의 95%에게 필요 없습니다.** 제작자끼리만 쓰는 기능이고, 실제 파일은 허깅페이스 쪽에 있으므로 그쪽 기능을 쓰면 됩니다.
- **기여 그래프(잔디)는 "매일 해야 한다"는 압박**을 줍니다. 취미로 로봇을 키우는 부모에게는 맞지 않을 수 있습니다.

## 4. 우리 쪽으로 옮기면

| 깃허브 개념 | 우리 커뮤니티에서 | 메모 |
|---|---|---|
| 저장소 | **경험팩 페이지** | 단, 파일은 우리가 보관하지 않고 허깅페이스 등에 연결만 (사업계획서 3-1 원칙 1) |
| README | **경험팩 카드의 "소개" 탭** (한국어 설명·설치 순서·영상) | 허깅페이스 모델 카드와 합쳐서 설계 (03 참고) |
| 릴리스 | **버전 기록 탭** — 버전마다 "무엇이 좋아졌나" 한 줄 | |
| 커밋 기록 | **되돌리기** — 설치 전 상태 저장 + 이전 버전으로 | 로봇 SDK가 지원하는 범위에서만 |
| 포크 | **"내 버전 만들기"** — 원작 표시가 따라붙는 변형 팩 | 특히 ②지시·③요구사항(우리 집 규칙·안전 설정) 변형에 유용 |
| 이슈 + 템플릿 | **"문제 알리기"** — 기종·펌웨어·바닥·영상 양식 | 해결되면 [해결됨] |
| Actions ✅ | **시뮬 검증 배지** | 사업계획서 4-1. Phase 0 기술 검증 과제 |
| 스타 | **"찜" 또는 "우리 집에도 있어요"** | 03의 좋아요와 합쳐서 하나로 |
| 조직 계정 | **학원·학교 계정** (교육 커리큘럼 팩 구독 단위) | 사업계획서 Phase 3 매출원 |
| Sponsors | **제작자 후원** | 사업계획서 Phase 3 |
