### S1. 공유 단위 — 경험팩 하나로 통일

- **확정안**: 행동 팩, 우리 집 규칙 팩, 안전 설정 팩을 모두 "경험팩"이라는 하나의 개념으로 다룹니다. "팩 찾기" 맨 위에 종류 탭(전체 · 행동 · 우리 집 규칙 · 안전 설정)을 둡니다. "묶음"은 여러 팩을 하나로 묶은 팩입니다 (예: "처음 산 날 세트").
- **이유**: 사업계획서 3-2의 ①~⑤가 원래 한 묶음으로 설계되어 있습니다. 메뉴를 따로 만들면 일반 소유자가 "규칙은 어디서 찾지?" 하고 헤매게 됩니다. 시뮬 검증은 행동 팩에만 해당하므로, 종류에 따라 카드에 보이는 칸만 달라집니다.
- **디자인 영향**: 카드 컴포넌트는 **하나**로 만들고, 종류 배지 4가지(색 또는 아이콘)로 구분합니다. 규칙·안전 팩 카드에는 검증 배지 자리를 비워 둡니다.

### S2. 핵심 개념 7개

- **확정안**: 04-2장의 K1~K7을 그대로 확정합니다.
- **보충**: 실기 보고(K5)는 글(K6)과 따로 저장합니다. 결과 숫자를 자동으로 계산해야 하기 때문입니다. 대신 성공한 보고는 해당 로봇의 커뮤니티 방 피드에도 "자랑"처럼 함께 보여 줍니다. 이렇게 하면 "경험은 이야기"라는 원칙 ③을 지킬 수 있습니다.
- **디자인 영향**: 피드에 섞이는 카드는 3종입니다. 글 카드, 해봤어요 카드, 팩 카드.

### S3. 신뢰 표시 — 별점 없이 "해봤어요"만

- **확정안**: 별점(★)을 두지 않습니다. 팩을 평가하는 방법은 "해봤어요" 하나뿐입니다.
  - 필수: 결과(성공 / 일부 성공 / 실패), 넘어짐 있었음(예/아니요), 내 로봇·펌웨어(자동), 바닥 종류(자동, 바꿀 수 있음)
  - 선택: 한 줄 소감, 영상(30초 이내 권장)
- **이유**:
  1. 초기에는 사람이 적습니다. 4명이 준 별점 3.5점은 아무것도 알려 주지 못하고 오해만 부릅니다.
  2. 일반 소유자가 정말 궁금한 것은 "좋은가"가 아니라 **"우리 집에서 되나, 넘어지나"**입니다.
  3. 별점과 해봤어요를 함께 두면 쓰는 사람은 쉬운 별점만 누릅니다. 그러면 정작 중요한 결과 데이터가 쌓이지 않습니다.
  4. 한 줄 소감 칸을 두어서 "이야기"가 들어갈 자리는 남겨 둡니다.
- **실패 보고는 숨기지 않습니다.** 실패가 보여야 성공 숫자도 믿을 수 있습니다.
- **디자인 영향**: 해봤어요 쓰기 화면은 **탭 3번 안에 끝나는 짧은 양식**으로 만듭니다 (결과 → 넘어짐 → 올리기, 나머지는 선택).

### S4. 숫자 표시 규칙

- **확정안**:
  - 해봤어요 5건 미만: `해봤어요 3 · 성공 2`처럼 **건수만** 보여 줍니다.
  - 5건 이상: `성공률 96% (46/48) · 넘어짐 4%`처럼 비율과 건수를 같이 보여 줍니다.
  - 시뮬레이션 결과는 따로 보여 줍니다: `시뮬 테스트 100회 · 넘어짐 3회`. 실기 숫자와 한 숫자로 합치지 않습니다.
  - 버전마다 숫자를 따로 셉니다. 카드에는 **최신 버전의 숫자**를 보여 주고, 버전 탭에서 이전 버전과 비교할 수 있게 합니다.
- **이유**: 2건 중 2건 성공을 "성공률 100%"라고 쓰면 과장입니다. 그리고 시뮬과 실제 집은 다른 시험이므로, 섞으면 둘 다 믿을 수 없게 됩니다.
- **디자인 영향**: 숫자 표시 컴포넌트에 두 상태(건수 모드 / 비율 모드)가 필요합니다. 시뮬 배지와 실기 숫자는 시각적으로 구분합니다.

### S5. 투표 — "도움 됐어요" 하나

- **확정안**: 글·댓글·답변에 "도움 됐어요" 버튼 하나만 둡니다. 비추천은 없습니다. 나쁜 글은 신고로 처리합니다.
- **이유**: 레딧식 비추천은 "넘어졌어요 ㅠㅠ" 같은 초보 질문을 아래로 묻어 버립니다. 그러면 초보는 다시 오지 않습니다. 우리 사용자의 80%가 일반 소유자입니다.
- **디자인 영향**: 반응 버튼은 하나입니다. 레딧처럼 ▲▼ 두 개가 나란히 있는 모양은 쓰지 않습니다.

### S6. 질문과 문제 — 한 탭, 두 종류

- **확정안**: 팩 상세의 "질문·문제" 탭 하나에 둘 다 모읍니다. 글을 쓸 때 [질문하기]와 [문제 알리기] 중 하나를 고릅니다.
  - 문제 알리기 양식: 로봇·펌웨어·버전(자동) / 바닥 / 어떤 일이 있었나 / 영상(선택)
  - 두 종류 모두 상태는 "열림 → 해결됨"으로 같습니다. 탭 안에서 종류와 상태로 걸러 볼 수 있습니다.
- **이유**: 일반인은 질문과 문제(버그)를 구분하지 못합니다. "자꾸 넘어져요"는 질문일까요, 문제일까요? 깃허브가 이 둘을 나누는 이유는 개발자들이 많은 신고를 분류해야 하기 때문입니다. 우리는 아직 그 정도 규모가 아닙니다.
- **디자인 영향**: 글 종류 칩 2개, 상태 배지 2개(열림/해결됨), 양식 화면 1개가 필요합니다.

### S7. 커뮤니티 방 — 5개로 시작

- **확정안**: 시작할 때 방은 5개입니다.

  | 방 | 성격 |
  |---|---|
  | 마이크로덕 방 | 기종 방 (12월 첫 배송에 맞춰 엶) |
  | Reachy Mini 방 | 기종 방 (이미 약 1만 대 보급) |
  | 다른 로봇 방 | 유니트리 등 나머지 기종. 기종 이름을 말머리로 붙임 |
  | 처음 왔어요 방 | 가입 인사, 첫 질문 |
  | 자유 방 | 그 밖의 이야기 |

  - **방 나누기 규칙**: "다른 로봇 방"에서 어떤 기종의 보유 인증 회원이 **30명**을 넘으면 그 기종만의 방을 엽니다.
  - "우리 집 규칙"은 방을 만들지 않고 팩(S1)으로 다룹니다. "교육" 방은 Phase 3에 엽니다.
- **이유**: 사업계획서 Phase 0의 목표는 보유 인증 100명입니다. 방이 많으면 방마다 글이 몇 개뿐이라 "죽은 커뮤니티"처럼 보입니다.
- **디자인 영향**: 방 목록은 처음엔 5개뿐이지만 늘어날 수 있게 설계합니다. 방마다 대표 이미지(로봇 사진)와 규칙 고정 영역이 필요합니다.

### S8. 원본 파일 연결 — v1은 링크만 (→ 3단계에서 개정)

> **개정 (3단계)**: 링크 + 공개 API로 기본 정보 자동 채우기. 아래 원래 내용 대신 2부 "S8·S11 개정"을 따릅니다.


- **확정안**: 제작자는 팩을 올릴 때 원본 위치(허깅페이스 저장소 등)의 주소를 붙여 넣고, 버전을 직접 적습니다. 우리 서비스는 그 주소를 보여 주고 [설치하기]를 누르면 로봇 회사의 공식 설치 경로로 넘겨줍니다.
- **이유**: 허깅페이스 서비스 약관상 외부 사이트가 자동으로 목록을 가져와도 되는지 아직 확인하지 못했습니다 (사업계획서 부록 C). 또 Phase 1에는 팩이 운영진이 만든 20개 정도라 손으로 입력해도 충분합니다.
- **다시 정할 때**: HF 약관을 확인했을 때, 또는 팩이 100개를 넘었을 때.
- **디자인 영향**: 올리기 마법사 첫 화면은 "원본 주소 붙여넣기"입니다. 팩 상세에는 "원본 위치" 링크를 작게 보여 줍니다.

### S9. 위쪽 메뉴

- **확정안**: `홈 · 팩 찾기 · 커뮤니티 · 챌린지 · 배우기 · 내 공간` + 오른쪽 위 `[+ 올리기]`
- **04 초안에서 바뀐 점**: "경험팩 찾기"는 "팩 찾기"로 줄였고, "라운지"는 "커뮤니티"로 바꿨습니다 (S14 용어집 참고).
- **모바일**: 아래쪽 탭 5개를 둡니다 (홈 · 팩 찾기 · [+] · 커뮤니티 · 내 공간). 챌린지와 배우기는 홈 화면 카드와 "더보기"에서 들어갑니다.
- **디자인 영향**: 데스크톱은 위쪽 내비게이션, 모바일은 아래쪽 탭바. 가운데 [+]를 누르면 "팩 올리기 / 글쓰기 / 해봤어요" 세 가지 중 하나를 고르는 시트가 열립니다.

### S10. 팩 상세 탭

- **확정안**: `소개 · 해봤어요(N) · 질문·문제(N) · 버전 · 변형(N)`. 변형 탭은 변형 팩이 1개 이상일 때만 보입니다 (변형 만들기 기능 자체는 2단계 기능인 A7).
- **디자인 영향**: 상단 요약 영역(이름·버전·배지·숫자·설치 버튼)과 탭 5개. 모바일에서는 설치 버튼을 화면 아래에 고정합니다.

### S11. 카드의 정해진 칸

- **확정안**: 04-3장의 표를 그대로 확정합니다. 필수 칸이 비면 공개할 수 없습니다.
- **디자인 영향**: 올리기 마법사는 이 칸 순서를 따릅니다. 카드(목록용)에는 이름·종류 배지·기종·난이도·숫자(S4)만 보여 줍니다.

### S12. 역할과 권한

- **확정안**: 04-7장의 7개 역할(방문자 · 회원 · 보유 인증 회원 · 제작자 · 방 관리자 · 공식 계정 · 운영진)을 확정합니다.
  - 해봤어요: **보유 인증 회원 이상만** 쓸 수 있습니다.
  - 팩 올리기: 제작자만 할 수 있습니다. 제작자가 되려면 보유 인증을 받은 뒤 첫 팩이 운영진 검토를 통과해야 합니다.
  - "라운지 관리자"는 "방 관리자"로 이름을 바꿨습니다 (S7).
- **디자인 영향**: 이름 옆 꼬리표 4종(보유 인증 ✓ · 제작자 · 공식 · 방 관리자)이 필요합니다.

### S13. 화면 형태 — 모바일 우선 반응형 웹

- **확정안**: 휴대폰 화면을 먼저 설계하고, 큰 화면에서는 넓게 펼치는 반응형 웹으로 만듭니다. 앱(앱스토어 설치형)은 Phase 3 이후에 검토합니다.
- **이유**: 해봤어요 영상은 휴대폰으로 찍습니다. 씨앗 커뮤니티(네이버 카페) 사용자도 대부분 휴대폰으로 들어옵니다. 앱을 바로 만들면 개발비가 두 배 들고, 앱 심사도 받아야 합니다.
- **디자인 영향**: 기준 화면 폭은 360px부터 시작합니다. 영상 올리기, 설치 버튼, 해봤어요 쓰기는 한 손으로 누를 수 있는 위치에 둡니다.

### S14. 이름과 용어

- **서비스 이름**: 가칭 **"로봇 습관"**
  - 고른 이유: 사업계획서의 핵심 비유("몸에 익은 습관 파일을 갈아 끼운다")와 맞습니다. 특정 브랜드 이름이 들어가지 않아서 여러 브랜드를 다루는 서비스에 어울립니다.
  - 다른 후보: "길들이기"는 동물을 조련하는 느낌이 있어서, 부모와 아이가 주로 쓰는 서비스에는 거리감이 있습니다. "뒤뚱"은 마이크로덕에만 맞아서 여러 브랜드를 다룬다는 원칙과 맞지 않습니다. 영문 후보 "HabitHub"는 습관 기록 앱들과 이름이 겹칠 가능성이 있습니다 (확인 필요).

### S8·S11 개정 — 허깅페이스 확인 결과 반영

- **S8 개정**: v1부터 **링크 + 공개 API로 기본 정보 자동 채우기**.
  - 제작자가 원본 주소를 붙여 넣으면, HF 공개 API와 마이크로덕 설명 파일(manifest)에서 **대상 기종·동작 종류·설치 자리·라이선스·최신 리비전**을 읽어 올리기 마법사의 칸을 미리 채움. 제작자는 확인·수정만 함.
  - 목록 전체를 주기적으로 긁어 오는 방식(자동 수집)은 하지 않음. 제작자가 등록한 주소만 읽음.
  - HF 사용량 제한(5분당 무료 계정 1,000회) 안에서, 로그인 토큰을 붙여 호출.
  - HF 로고는 쓰지 않음. 카드 본문을 옮겨 실을 때는 그 저장소 라이선스를 따름.
  - 이유: 약관에서 링크·공개 API 사용을 막는 조항을 찾지 못했고, 마이크로덕은 설명 파일이 표준화되어 있어 자동 채우기 효과가 큼 (일반인 5분 원칙 ②). **현재 약관 원문을 직접 확인하지 못했으므로 출시 전 HF에 확인**하는 조건은 그대로 둠.
- **S11 보충**: 카드에 **자동 칸 2개** 추가
  - **설치 자리**: 마이크로덕 설명 파일의 slot ("걷기 자리", "서기 자리", "새 기술" 등) → 사용자는 "이 팩을 깔면 지금 걷기 방식이 바뀝니다"처럼 알게 됨
  - **동작 종류**: 한 번 하는 동작 / 계속하는 동작 / 정해진 순서 동작
- 근거: evidence 3-1, 3-3
